# 鸟群队列跟随系统 Gameplay 设计

> 文档定位：M4 前置玩法设计，只规定玩家可感知的鸟群规则、状态、阈值语义与验收效果；不规定 C++ 类、组件、行为树资产、Blackboard Key 或文件结构。
>
> 核心结论：初版采用“确定性队列拓扑 + 连续 Steering/施力 + 少量离散状态”的混合方案。不要把逐帧距离控制写成行为树，也不要让所有鸟直接追逐主控鸟。

## 1. 体验目标

四只鸟应表现为一支会排队、会等待、会补位的小队：

- 主控鸟由玩家直接控制，相机始终绑定当前主控鸟。
- 其他鸟沿队伍已经实际走过的路线依次跟随，而不是同时聚集到主控鸟脚下。
- 队伍在安全范围内保持放松；只有落后到一定距离时才施加追赶移动。
- 主控切换后，队伍拓扑平滑重排，原主控变为普通跟随鸟。
- 跳跃不是所有鸟同时复制主控输入，而是作为沿队伍路径传播的“动作事件”；每只鸟到达相同障碍或高度差时再跳。
- 跟随鸟暂时被阻挡、落后或跳跃失败时有可读的追赶与恢复规则，不会永久丢失。

本系统服务于四只固定角色，不追求几十上百单位的通用群集模拟。

## 2. 为什么不选择纯行为树

### 2.1 连续跟随属于 Steering，不属于高层决策

成熟的自主角色方案通常将运动拆成三层：

1. **Action Selection**：当前是跟随、等待、回收还是交互。
2. **Steering**：应该朝哪个方向、以多大力度移动，如何减速和分离。
3. **Locomotion**：角色实际的地面移动、重力和跳跃。

队伍距离、到达减速、邻居分离和空中追赶都需要持续更新。将这些计算放进行为树 Service/Task，会引入不必要的 Blackboard 同步、节点切换和 Tick 间隔问题，而且很难保证四只鸟在同一规则下产生稳定队形。

### 2.2 行为树适合离散行为，但本项目初版不必为此引入

行为树或 StateTree 适合表达：

- 正常跟随；
- 等待主控；
- 脱队追赶；
- 卡住恢复；
- 发射后自动回归；
- 执行鸟种专属交互。

但 M4 只有四只鸟，且核心状态少、转换明确。建议初版直接采用确定性状态规则；后续如果加入战斗、自动采集、侦察和复杂鸟种职责，再考虑用 StateTree/行为树负责高层状态，底层仍调用同一套队列 Steering。

Epic 将 StateTree 定义为结合行为树 Selector 与状态机 State/Transition 的高性能层级状态机，因此它比传统行为树更适合未来承载“跟随/等待/发射/回收/工作”等少量长期状态；但它不应替代每帧移动控制。

## 3. 队伍数据概念

### 3.1 大部队成员

鸟在下列状态时属于“大部队”成员：

- 当前主控鸟；
- 正常跟随主控、没有进入独立行动的鸟；
- 正在按队列追赶或按跳跃事件通过障碍的鸟。

正在被弹弓发射、执行侦察、自动回收材料或明确脱队的鸟暂时不参与队列拓扑，也不能成为其他鸟的前导目标。它归队后再插入队尾。

### 3.2 队伍不是每帧重算的最近邻图

“跟随距离最近的大部队鸟”这个直觉是合理的，但如果每帧单纯重算最近邻，会产生三个问题：

- 两只鸟距离接近时，目标会来回切换，形成抖动。
- 可能产生 A 跟 B、B 又跟 A 的环，失去与主控的连通关系。
- 主控转弯或队伍交叉时，鸟会抄近路穿过队形，而不是沿路线排队。

因此使用**以主控为根的有向队列树**：每只跟随鸟只有一个前导鸟，沿前导链最终一定到达主控。前导优先选择队列中位于自己前方、仍属于大部队且距离最近的鸟。选定后保持一段时间，只有前导失效、距离严重异常或队伍重排时才更换。

初版四鸟建议保持单链：

```text
主控 -> 跟随 1 -> 跟随 2 -> 跟随 3
```

未来鸟数增加后可扩展为两列或小型树，但必须继续保证无环和所有成员可追溯到主控。

### 3.3 路径历史带

每只大部队鸟都在其实际运动轨迹中留下低频路径样本，至少包含：

- 球面方向或 CellTopo 区域；
- 连续表面位置；
- 当时的切向前进方向；
- 时间或累计路程；
- 是否发生起跳、落地、跨河、窄口等动作事件。

跟随鸟的目标不是“前导鸟当前坐标”，而是前导鸟路径上向后偏移一定累计路程的样本。这个 **follow-the-leader / breadcrumb trail** 规则可以让后排鸟复现前排的转弯路线，避免切弯、挤成一团和在球面上使用世界坐标偏移造成畸变。

CellTopo 仍是路径语义、道路、水网和障碍判定的逻辑源；连续路径点只服务于移动表现与局部施力。

## 4. 地面跟随规则

### 4.1 距离迟滞：范围内不施加跟随力

每只跟随鸟比较自己与目标路径样本的球面/表面距离，使用两个阈值：

- `FollowStartDistance`：超过后进入追赶并施加移动力。
- `FollowStopDistance`：追赶后缩短到该距离以内才停止跟随力。

必须满足 `FollowStopDistance < FollowStartDistance`，以免边界附近每帧启停。范围内没有跟随力时，鸟仍受自己的径向悬挂、重力和阻力影响，因此会自然停稳，而不是被冻结或被传送到槽位。

建议体验初值：

| 规则 | 建议值 | 体验意义 |
| --- | ---: | --- |
| 队列槽位路程间隔 | 160–220 cm | 大于单只鸟的视觉宽度，形成明确队列。 |
| `FollowStartDistance` | 220–280 cm | 前导拉开后才开始行动。 |
| `FollowStopDistance` | 120–170 cm | 进入舒适区后停止追逐，避免贴脸。 |
| 个体最小分离距离 | 80–110 cm | 防止碰撞体和模型重叠。 |
| 严重脱队距离 | 900–1400 cm | 进入快速追赶或恢复流程。 |

实际值应按鸟模型尺寸和 `680 cm/s` 的主控终端速度在 M4 试玩中调整。

### 4.2 追赶施力

追赶力由以下意图组合：

```text
FollowIntent     = 朝目标路径样本移动，并在接近时减速
SeparationIntent = 与邻近鸟保持最小间距
PathIntent       = 尽量留在前导鸟的历史路径带内
ObstacleIntent   = 绕开树木、建筑和其他局部阻挡
```

优先级建议：

1. 避免即时碰撞；
2. 保持地表与处理跳跃；
3. 回到路径带；
4. 到达队列槽位；
5. 轻微分离与朝向对齐。

不要单纯把多个单位向量等权相加。即时避障和地表安全应覆盖队形美观；到达目标使用 Arrival 式减速，避免越过目标后反复回头。

### 4.3 不使用经典 Boids 的凝聚中心

经典 Boids 的 Separation、Cohesion、Alignment 适合鸟群飞行或鱼群，但本项目需要排队跟随。可借用：

- **Separation**：避免拥挤；
- **Alignment**：低权重匹配前导的切向方向；
- **Arrival / Leader Following**：接近后减速。

不采用全体质心 Cohesion 作为主要目标，否则三只跟随鸟仍会自然围到主控附近。队列路径样本取代全局凝聚中心。

## 5. 主控切换

玩家用 Tab/HUD 选择任意可控鸟后：

1. 相机切换并平滑绑定新主控鸟。
2. 新主控立即成为队伍根节点，停止自动跟随输入。
3. 原主控保留当前速度，转为跟随状态，避免瞬间刹停。
4. 根据所有在队成员沿现有路径历史到新主控的顺序，重新建立无环队列。
5. 队列目标在短暂重排时间内从旧槽位平滑过渡到新槽位，不瞬移、不调换世界位置。
6. 新主控在空中时，其原有空中状态继续由玩家控制；地面鸟不会因主控切换立刻起跳，只有接收到有效路径动作事件才跳。

如果新主控原本在队尾，最自然的视觉结果是队伍逐渐掉头并按新路径重新排队，而不是把整个队列逻辑瞬时反转后互相穿越。

## 6. 跳跃跟随：传播动作事件，而不是复制按键

### 6.1 为什么不能延迟复制 Space

按固定时间延迟复制主控跳跃，会在以下情况失败：

- 后排鸟速度不同，延迟结束时尚未到达障碍。
- 主控在运动中起跳，后排到达跳点的实际时间随队列间距变化。
- 主控切换、发生碰撞或绕行后，世界坐标跳点已经不再适用。
- 球面不同位置的 `Up` 不同，不能复用同一个世界空间冲量方向。

因此主控跳跃应在路径历史中生成一个 **Jump Event**。

### 6.2 Jump Event 的玩法语义

事件记录：

- 起跳在队伍路径上的累计路程位置；
- 起跳 CellTopo 区域和连续表面点；
- 起跳前行进方向；
- 主控起跳速度或跳跃强度档；
- 起跳前后地表目标半径/高度差；
- 主控落地点或落地路径位置；
- 事件有效期和所属路径版本。

每只跟随鸟沿自己的前导路径接近事件，而不是比较与主控当前世界位置的直线距离。

### 6.3 按需跳跃条件

跟随鸟只有同时满足下列条件才执行事件：

1. 自己仍属于该事件对应的队列路径。
2. 已到达起跳触发带，而不是仅仅时间到了。
3. 自己处于接地或可起跳状态。
4. 前方路径的目标地表高度比当前可步行高度高出 `JumpHeightTrigger`，或者前导鸟已进入空中且两者径向高度差超过 `AirFollowHeightThreshold`。
5. 预计起跳方向没有被近距离障碍完全封死。

如果路径连续平缓、鸟已经通过其他路线到达目标高度，即使路径中存在旧 Jump Event，也可以跳过，体现“按需跳跃”。

建议体验初值：

| 规则 | 建议值 |
| --- | ---: |
| 起跳触发带前缘 | 跳点前 70–120 cm |
| `JumpHeightTrigger` | 45–75 cm |
| `AirFollowHeightThreshold` | 80–130 cm |
| 起跳事件等待上限 | 1.0–1.8 s |
| 落地确认高度误差 | 15–30 cm |

### 6.4 空中跟随

鸟起跳后仍使用与主控相同的径向重力和移动模型，但控制目的不同：

- 径向运动由跳跃初速和球心重力决定。
- 跟随 AI 只施加受限的**切向空中控制力**，朝 Jump Event 的落地区域或前导鸟对应路径样本修正。
- 不直接朝空中的前导鸟三维位置施力，避免四只鸟在空中互相吸附或改变正常抛物线。
- 空中 Separation 权重降低，只处理明显碰撞风险。
- 接近落地区域后优先对齐落地切向方向，不强求空中维持固定间距。

如果前导鸟只是从坡缘短暂腾空、径向高度差未超过阈值，后排鸟可以继续地面移动并等待；只有路径断裂或高度差足以阻挡地面通过时才跳。

### 6.5 跳跃失败与恢复

- **未起跳**：在跳点前等待短时间，再次检查接地和净空；不可无限叠加跳跃输入。
- **撞到障碍**：按当前物理落地，不在空中瞬移；落地后重新追踪尚未消费的事件。
- **落在错误一侧**：进入快速追赶，必要时使用一次受控补跳。
- **事件过期或路径已重建**：丢弃事件，按新前导路径重新判断。
- **严重脱队且不可达**：先回收到队伍最后一个安全路径样本附近，而不是直接传送到主控脚下；回收应有短暂淡出/落羽表现。

## 7. 避障与道路/CellTopo 的关系

本项目不为球面建立全球平面 NavMesh。UE Navigation System 的成熟范式是从碰撞几何生成 NavMesh 多边形图，再按成本寻路，并可用特殊连接跨越非连续区域；这些思路可以借鉴，但本项目的全局逻辑图已经是 CellTopo。

因此：

- **全局/中程路径**：沿主控和前导实际走过的 CellTopo/路径历史传播。
- **道路倾向**：道路 Cell 的跟随代价更低，队伍自然保持在道路走廊。
- **河流/桥梁**：水边和桥址是 CellTopo 边语义，跟随鸟复用主控已通过的合法边；不能为了追近而直穿河流。
- **局部避障**：只在当前位置附近进行短程障碍预测和切向绕行。
- **不可达恢复**：依据安全路径样本和 CellTopo 连通性判断，而不是用世界直线距离强行拉回。

EQS 适合从多个候选位置中按测试评分选出最优点，可用于未来选择临时等待位、掩体或交互位；四鸟队列的目标槽位已经由路径历史确定，不需要每帧运行 EQS。

## 8. 状态与转换

Gameplay 上每只非主控鸟只需表现出以下状态：

| 状态 | 进入条件 | 玩家可见行为 |
| --- | --- | --- |
| `RelaxedInFormation` | 位于舒适区内 | 不施加跟随力，自然停稳并播放待机。 |
| `Following` | 超过启动距离 | 沿前导路径施力追赶，接近后减速。 |
| `WaitingForJump` | 到达跳点但暂不可跳 | 在跳点前等待、调整朝向。 |
| `FollowingInAir` | 消费 Jump Event 后离地 | 使用受限切向空中控制对准落地区域。 |
| `CatchingUp` | 超过严重脱队距离 | 提高追赶力和允许速度，降低队形美观权重。 |
| `Recovering` | 长时间无进展或逻辑不可达 | 返回最近安全路径样本后插入队尾。 |
| `DetachedActivity` | 发射、侦察、自动回收等 | 暂不属于队列，完成后再归队。 |

状态转换应带时间和距离迟滞。尤其不能用单一距离阈值在 `RelaxedInFormation` 与 `Following` 之间来回跳。

## 9. 调参原则

1. 先确定模型尺寸和舒适间距，再调移动力。
2. 队列间距应按路径累计路程计算，不用世界直线距离。
3. 跟随最大追赶速度可以略高于主控，但只在落后时启用；否则队尾永远追不上持续满速主控。
4. Separation 只负责避免重叠，不应强到破坏队列顺序。
5. 空中控制明显弱于地面控制，不允许横向“飞”向主控。
6. 队伍重排应优先保持世界位置连续，而不是立刻获得完美队形。
7. 回收是最后保险，不应掩盖正常跳跃和避障失败；需要记录触发原因以便调试。

## 10. M4 Gameplay 验收场景

### 10.1 平地与转弯

- 主控直线移动，三只鸟依次启动并形成清楚的前后队列。
- 主控停止后，后排进入舒适区便停止，不全部挤到主控身边。
- 主控做 S 形转弯，后排沿路径带转弯，不大幅切角或交换顺序。

### 10.2 主控切换

- 从队首切到队尾，相机绑定新主控，原主控平滑转为跟随。
- 队伍不瞬移、不互穿；短暂重排后所有前导链可回溯到新主控。
- 连续切换不能生成循环前导或遗失成员。

### 10.3 跳跃

- 主控越过明显高度差，后排依次到达同一跳点后按需跳跃。
- 高度差不足时后排继续走，不机械复制跳跃。
- 跟随鸟在空中能有限修正落点，但仍呈现自然径向弹道。
- 主控落地后后排仍在空中时，队伍不会把空中鸟判定为永久脱队。

### 10.4 水网、道路与障碍

- 主控过桥后，后排沿桥通过，不按世界直线切入河道。
- 道路弯曲时队列遵循主控路径，不直接穿越森林或山体捷径。
- 一只鸟被局部障碍阻挡时，其他鸟不会全部回头围住它；该鸟独立追赶或恢复。

### 10.5 稳定性

- 在舒适区边缘站立 10 秒，不出现反复启停。
- 四鸟没有持续重叠、目标来回切换或 A/B 互相跟随的环。
- 正常游玩中不频繁触发 Recovering；一旦触发，返回队尾而不是主控脚下。

## 11. 研究依据与取舍

本设计参考了以下成熟方案，但按球面 CellTopo 和四鸟玩法进行了取舍：

1. Craig Reynolds 的 Steering Behaviors 将运动分为 action selection、steering、locomotion 三层；其 Arrival、Path Following、Separation、Leader Following 和行为组合直接支持本设计的“高层状态 + 连续转向 + 共用移动模型”。Leader Following 使用领导者后方偏移目标、Arrival 减速与 Separation 防拥挤，但本项目进一步改为路径历史队列，避免球面转弯时切角。
2. Reynolds 的 Path Following 使用“路径脊线 + 容许半径”的走廊，而不是把角色刚性锁在轨道上；本设计将其映射为 CellTopo 路径语义与连续 breadcrumb 路径带。
3. Epic UE 5.8 Behavior Tree/EQS 文档说明 EQS 用生成器、上下文和测试对候选项评分，并可由行为树调用；它更适合等待位、掩体、交互位选择，不适合取代确定的队列槽位与逐帧 Steering。
4. Epic UE 5.8 StateTree 文档将 StateTree 描述为结合行为树 Selector 与状态机 State/Transition 的层级状态机，适合未来管理跟随、等待、发射和回收等长期状态。
5. Epic UE 5.8 Navigation System 文档说明 NavMesh 将碰撞几何切分为多边形图、使用成本寻找最优路径并支持非连续连接；本项目不建立全球 NavMesh，而是由 CellTopo 图承担道路、水边和桥梁等中程路径语义。
6. Epic UE 5.8 MassEntity/Mass Avoidance 提供面向大量实体的数据导向与基于力的避让。四鸟规模无需引入 Mass，但可借鉴“局部避让力与高层路径解耦”的原则。

## 12. 最终建议

M4 初版应实现为规则明确的混合系统：

- 队伍管理负责无环前导链、主控切换和成员资格。
- 路径历史负责队列槽位、转弯复现和 Jump Event 传播。
- 连续 Steering 负责 Arrival、Path、Separation 与局部避障意图。
- 所有鸟复用同一套力模型、径向悬挂、重力和跳跃能力。
- 简单离散状态负责等待、空中跟随、追赶和恢复。

不要在 M4 为四只鸟先搭建通用行为树。等鸟种自动交互、侦察、回收和战斗职责增多后，再用 StateTree或行为树编排高层任务；底层队列与跳跃事件系统保持不变。
